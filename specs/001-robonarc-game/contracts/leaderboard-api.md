# Contract: Leaderboard API (Supabase / PostgREST), v2

Client: `LeaderboardClient` (`src/game/services/leaderboard_client.gd`), owned by the
`Leaderboard` autoload (`LeaderboardService`, `src/game/services/leaderboard_service.gd`),
which also owns the queue of unsent shifts, the cached board, and the retry timer.
Base URL and anon key live in a `LeaderboardConfig` resource (`base_url`,
`anon_key`, `enabled`): the committed `data/game/leaderboard_config.tres` is
disabled and empty; a gitignored `data/game/leaderboard_config.local.tres` (hand
written, or generated by CI from the `SUPABASE_URL` / `SUPABASE_ANON_KEY` secrets)
takes precedence. A missing or disabled config makes every call emit `failed`
immediately with reason `DISABLED`, so the game runs with no service configured.
The anon key is Supabase's public client key; keeping it out of git is hygiene,
not a security boundary (the private table and the two RPCs are).
`LeaderboardConfig.submit_from_editor` (default false) keeps editor runs read-only:
they fetch the board but skip submits with reason `DISABLED` and queue nothing.
Exports always submit.

## Identity model

A shift is either **named** (email + first name + last initial) or **anonymous**.
The email is the board's unique key and is never returned to any client: a
returning player's shifts collapse into one board entry, their best score, shown
as `First L.` from the best shift. Each anonymous shift is its own entry, named
`anonymous NN` by the server from a sequence in arrival order (`01`, `02`, ...).

## Table `public.shifts`

One row per submitted shift. Private: the anon role has no grants and RLS has no
policies; only the RPCs below (security definer) read or write it.

| Column | Type | Constraint |
|--------|------|------------|
| id | bigint identity | primary key |
| submission_id | uuid | unique; client-generated (`Uuid.v4()`) |
| created_at | timestamptz | default now() |
| email | text, nullable | null for anonymous; lower-cased and trimmed, `<= 254`, `^[^\s@]+@[^\s@]+\.[A-Za-z]{2,}$` |
| first_name | text, nullable | `char_length between 1 and 12 and ~ '^[A-Za-z]+$'`; null iff email null |
| last_initial | text, nullable | `~ '^[A-Z]$'`; null iff email null |
| anon_no | integer, nullable | trigger-assigned from `anonymous_seq` when email is null |
| score | integer | `score between -5000 and 50000` |
| correct / wrong / missed / empty | integer | `>= 0` |
| duration_sec | integer | `between 10 and 600` |
| client | text | e.g. `web`, `windows`, `android`, `editor`; default `unknown` |
| f1 | numeric(4,3), nullable | the shift's F1 score (`F1Score`), 0..1 |

Indexes: `shifts_score_desc_idx (score desc, created_at asc)`, `shifts_email_idx (email)`.

## Function `public.top_scores(p_limit integer default 20)`

`security definer`, `stable`, granted to `anon`. Returns
`setof (rank integer, name text, score integer, f1 numeric)`: one entry per player (best
shift per email, every anonymous shift), ordered by `score desc, created_at asc`,
limited to `least(p_limit, 100)`. `rank` is `rank()` over score, so ties share the
better rank. `name` is the server-built display name.

## Function `public.submit_shifts(p_shifts jsonb)`

`security definer`, granted to `anon`. Takes an array of at most 50 shift objects,
inserts them (`on conflict (submission_id) do nothing`, so a resend after a lost
answer adds no row), and returns one receipt per input shift, in input order:
`(submission_id uuid, rank integer, name text, best_score integer)`. `rank` and
`best_score` describe the player's board entry, which for a returning player may
be an earlier, better shift. Any row failing a CHECK fails the whole batch
(HTTP 400): the client validates first and drops a rejected batch rather than
retrying it forever.

## Requests

All requests send headers:

```text
apikey: <key>
Content-Type: application/json
Authorization: Bearer <key>     # legacy anon JWT keys only
```

`<key>` is the project's public client key. Current projects issue a
"publishable key" (`sb_publishable_...`); it is not a JWT and Supabase rejects it
as a Bearer token, so the client sends it in `apikey` only. Legacy anon keys are
JWTs and go in both headers. The secret key and the JWKS URL are never used.

Timeout: `request_timeout_sec` (tunable, 5 s). No retries inside the client; the
service retries whole batches (below).

### Fetch top scores

```text
POST {base_url}/rest/v1/rpc/top_scores
{"p_limit": 15}
```

Response `200`: `[{"rank":1,"name":"Ava K.","score":2450,"f1":0.87},{"rank":2,"name":"anonymous 07","score":900,"f1":0.41}, ...]`

`f1` is the best shift's F1 (null on rows written before v2.1; displayed as `-`).

Client emits `top_scores_received(entries: Array[LeaderboardEntry])`. Names that
are empty or contain anything but letters, digits, spaces, and dots display as
`"???"`; names longer than 16 are truncated. The service caches every successful
answer in `user://board_cache.json` and shows it while offline.

### Submit shifts

```text
POST {base_url}/rest/v1/rpc/submit_shifts
{"p_shifts":[
  {"submission_id":"6f1c...","email":"ava@example.com","first_name":"Ava","last_initial":"K",
   "score":2450,"correct":26,"wrong":2,"missed":3,"empty":5,"duration_sec":90,"f1":0.867,"client":"web"},
  {"submission_id":"a9e2...","email":null,"first_name":null,"last_initial":null,
   "score":-15,"correct":0,"wrong":1,"missed":2,"empty":0,"duration_sec":90,"f1":0,"client":"web"}
]}
```

Response `200`:

```json
[{"submission_id":"6f1c...","rank":3,"name":"Ava K.","best_score":2450},
 {"submission_id":"a9e2...","rank":41,"name":"anonymous 07","best_score":-15}]
```

Client emits `batch_submitted(receipts: Array[SubmitReceipt])`; on any failure
emits `failed("submit", reason)`.

## Queue and retry (`LeaderboardService`)

- `submit(result)` assigns a `submission_id` if missing, appends the shift to
  `user://pending_shifts.json`, and calls `flush()`. Shifts leave the file only when
  a receipt names them.
- `flush()` sends the oldest 50 waiting shifts as one batch, unless one is out.
  It runs at startup, on every title screen visit, after every successful fetch
  (proof the board is reachable), and `sync_retry_sec` (tunable, 30 s) after a
  failed batch.
- Reasons `HTTP_400` and `HTTP_422` are rejections: the batch is dropped with a
  warning. Everything else keeps the shifts and retries.

## Sync status

The service reports one `Status` the screens colour their indicator with:

| Status | Colour | Meaning |
|--------|--------|---------|
| SYNCED | green | last request succeeded and nothing is waiting |
| SYNCING | yellow | a fetch or batch is in flight |
| OFFLINE | red | last request failed; shows how many shifts are waiting |
| DISABLED | grey | no board configured |

## Failure reasons

`DISABLED`, `TIMEOUT`, `NETWORK` (result != RESULT_SUCCESS), `HTTP_<code>`,
`BAD_JSON`. A failed fetch keeps the cached board on screen with the note
"showing the last synced board" (or "leaderboard unavailable" with no cache);
a failed submit shows "Saved. It will post when the board is back online." on
the results screen. None block.

## Concurrency

At most one in-flight fetch and one in-flight batch; a new fetch or batch while
one is pending is ignored (the pending answer is used). The service is an
autoload, so a screen may leave mid-request without losing anything.
